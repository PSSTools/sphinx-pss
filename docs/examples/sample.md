# Example: a DMA subsystem

Everything below is generated by this extension from
`tests/fixtures/pss/dma_pkg.pss` and `tests/fixtures/pss/dma_ext.pss` in this
repository — the same files the test suite asserts against. Nothing on this page
is written by hand, so if the extension breaks, this page breaks with it.

The model is small but covers one of everything Phase 1 documents: a package, a
component with actions, flow-object references, a resource claim, each
flow-object kind, a plain struct, an enum, named constraints, a function, and
both `rand` and plain attribute fields.

## Flow objects

The four flow-object kinds. What distinguishes them is not their contents but
their scheduling semantics — a buffer is complete before its consumer runs, a
stream is concurrent with it, a state persists between actions, and a resource
is claimed rather than passed.

into the base type, which is what makes the linked model the right view to
document — and why extension provenance is recorded (it is rendered from Phase

### Its actions

`Configure` must run before any transfer. Nothing states that ordering directly
— it falls out of `Configure` producing the `EngineState` that `Xfer` consumes,
which is how PSS expresses scheduling constraints.

```{eval-rst}

```

`Xfer` is the interesting one: it consumes a state, produces a buffer, claims a
